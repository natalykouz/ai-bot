# LEGACY_NEWSLETTER_FLOW.md

## Назначение документа

Проектный документ UX/state-flow будущей функции Telegram-бота
**«Создать рассылку на основе старого письма»**.

Это **не техническая архитектура** и **не реализация** — код проекта этим
документом не менялся, функция не реализована.

## Что изменилось относительно предыдущей версии

Предыдущая версия этого документа ошибочно описывала **покомпонентную
интерактивную миграцию**: разобрать старое письмо на блоки → показать
список блоков → по каждому блоку спросить «оставить / изменить / убрать» →
собрать новое письмо заново из решений пользователя. Такого flow **не
будет** — пользователь не редактирует письмо через Telegram.

Актуальная задача проще и зафиксирована целиком в этой версии документа:

> взять старое письмо **целиком** как исходник → определить его формат →
> в зависимости от формата сохранить исходный HTML (UniSender) или
> адаптировать его к текущей канонической библиотеке (Letteros) → заменить
> расписание на актуальное → вернуть **один готовый HTML-файл** целиком.

Убрано полностью: отчёт по блокам, экран «оставить/изменить/убрать»,
ручной подбор компонента пользователем, цикл ввода текста по каждому блоку,
переключение на flow «Генерация письма» как запасной вариант. Ничего из
этого не реализовывать.

## Обновление: Letteros — основной сценарий, не unsupported/fallback

**Убрана прежняя фиксация «Letteros пока обрабатывается как
неподдерживаемый формат».** Она была верна на момент написания (тогда в
проекте не было ни одного формализованного способа сопоставить
Letteros-фрагмент с библиотекой), но перестала быть верной: в проект добавлен
`mail_project/letteros_components.zip` — каноническая библиотека Letteros
ровно с тем же множеством `module`/`element`, что и `unisender_components.zip`
(см. `LEGACY_NEWSLETTER_MIGRATION.md` §2.5). Имя Letteros-компонента
напрямую задаёт соответствующий UniSender-компонент — отдельный mapping не
нужен. Большинство реальных production-писем проекта свёрстаны именно в
Letteros — это основной, а не запасной или маловероятный сценарий функции.

Фактическая модель (заменяет прежнюю целиком):

```
Letteros HTML
  → автоматическое распознавание известных компонентов из letteros_components
  → перенос содержимого в одноимённые canonical UniSender-компоненты
  → замена расписания (существующая цепочка, без изменений)
  → сборка целого HTML
  → готовый файл для загрузки в UniSender
```

Первое звено этой цепочки — распознавание — **реализовано и покрыто
тестами** (`mail_project/letteros_recognition.py`,
`mail_project/test_letteros_recognition.py`, см. раздел 6). Остальные звенья
(перенос содержимого, сборка) — не реализованы, это следующий шаг работы, не
этой сессии.

**Правило, зафиксированное явно, без права ослаблять:** если фрагмент
Letteros-письма не удаётся надёжно сопоставить с компонентом из
`letteros_components` — нельзя угадывать его тип. Такой случай — ошибка
разбора конкретного письма (см. раздел 7), а не повод придумать компонент
"по смыслу" или молча пропустить содержимое.

## 1. Пользовательский сценарий

СММ-менеджер хочет сделать новую рассылку, взяв за основу старую.

1. Менеджер открывает раздел «Email-рассылки» и выбирает операцию
   «Создать рассылку на основе старого письма».
2. Бот просит прислать HTML старого письма.
3. Менеджер присылает файл.
4. Бот автоматически определяет формат письма — без вопросов менеджеру.
   - Если это письмо, уже собранное из нашей UniSender-библиотеки — бот
     запрашивает `SCHEDULE.txt` с актуальным расписанием и заменяет
     расписание в письме, не трогая остальное содержимое и структуру.
   - Если это письмо из Letteros (основной сценарий — см. «Обновление»
     выше) — бот распознаёт в нём известные компоненты канонической
     Letteros-библиотеки, переносит их содержимое в одноимённые
     UniSender-компоненты, сохраняя содержание и визуальную структуру
     настолько, насколько это позволяет библиотека, и так же заменяет
     расписание. Распознавание **реализовано**; перенос содержимого и
     сборка результата — пока нет (см. раздел 6). Если фрагмент письма не
     удаётся надёжно сопоставить с компонентом библиотеки — это не повод
     угадывать: разбор этого письма останавливается с ошибкой (раздел 7).
   - Если формат не удаётся отнести ни к UniSender, ни к Letteros — бот
     сообщает, что формат не поддерживается, и останавливает flow. Ничего
     не импортируется и не собирается частично.
5. Менеджер получает один готовый HTML-файл (или сообщение об остановке) —
   без промежуточных решений о содержимом письма.

Менеджер не должен на любом шаге видеть внутренние термины
(`em="block"`, `letteros-element`, `letteros-module`, canonical HTML) —
только понятия «старое письмо», «расписание», «новая рассылка», «формат не
поддерживается».

## 2. Точка входа

Без изменений относительно предыдущей версии. Существующее подменю
«Email-рассылки» сейчас показывает две кнопки (`btn_email_menu`,
`handlers/generation.py:133-148`): «Генерация расписания» и «HTML-основа
письма из SCHEDULE.txt». Новая функция добавляется в это же подменю третьей
видимой кнопкой:

```
Email-рассылки:
[ Генерация расписания ]
[ HTML-основа письма из SCHEDULE.txt ]
[ Создать рассылку на основе старого письма ]   ← новое
```

Запуск — по нажатию этой кнопки, тем же паттерном (`callback_query`, сброс
состояния FSM, переход в первое состояние нового flow), что и остальные
операции подменю.

## 3. Шаг 1 — Загрузка старого письма

Без изменений относительно предыдущей версии. Сразу после выбора функции
бот просит файл — без промежуточных вопросов, по аналогии с `start_qa()`
(`handlers/generation.py:1173-1182`) и `start_schedule_txt_fish()`
(`handlers/generation.py:411-420`):

> «Пришлите HTML старого письма документом.»

Проверки при получении файла — по аналогии с `receive_qa_html()`
(`handlers/generation.py:1185-1199`):

- расширение `.html`/`.htm`;
- файл не пустой после декодирования.

Если проверка не проходит — бот просит прислать файл ещё раз или отменить
(`/cancel`), не переходя дальше.

## 4. Шаг 2 — Определение формата письма

Полностью автоматический шаг. **Пользователю не задаётся ни одного
вопроса о формате** — это прямое отличие от предыдущей версии документа
(там был уточняющий вопрос «Letteros / UniSender / не знаю»). Формат
определяется системой, и по каждому из трёх исходов дальнейшее поведение
жёстко зафиксировано требованиями, а не выбором пользователя.

### 4.1. Признак «это письмо уже из UniSender»

Переиспользуется существующий механизм поиска канонических блоков —
тот же тип разбора, что уже используется для «Проверка качества письма»
(`qa.find_components()`, регэксп по `letteros-element`/`letteros-module` +
`generation._scan_balanced_tr_end()` — см. `LEGACY_NEWSLETTER_MIGRATION.md`
§3.1). Если в загруженном HTML находится хотя бы один такой блок — письмо
классифицируется как **UniSender**. Этот же порог («хотя бы один найденный
блок») уже используется в проекте как условие «в этом HTML вообще есть что
проверять» (`qa.py:264`) — новый порог не вводится.

**`DECISION NEEDED` (унаследовано из `LEGACY_NEWSLETTER_MIGRATION.md`
§1.2):** на какой именно маркер опираться — `letteros-element`/
`letteros-module` (как сегодня делает `qa.find_components()`), `em="block"
class="em-structure"`, или оба одновременно. Выбор не меняет форму flow —
в любом случае результат один из трёх дискретных исходов — но влияет на
то, сколько реальных писем будет уверенно распознано как UniSender.

### 4.2. Признак «это письмо из Letteros»

Есть теперь два независимых сигнала, один из них — код, не только
документированное наблюдение:

1. **Признаки-строки** — вручную зафиксированные по одному реальному
   примеру (`LEGACY_NEWSLETTER_MIGRATION.md` §2.2): пиксель/редиректор
   `api.letteros.com/pixel/...`, CDN `static.letteros.com`/`s3.letteros.com`,
   служебные атрибуты `bis_size`/`bis_id`, плейсхолдеры
   `{{UnsubscribeUrl}}`/`{{WebLetterUrl}}`. По-прежнему выведены из одного
   примера, не гарантированно полны.
2. **Совпадение хотя бы одного кандидата в `letteros_recognition.recognize_components()`**
   (реализовано, см. раздел 6) — даже без структурного подтверждения, сам
   факт, что в письме нашёлся хотя бы один фрагмент с «подписью»,
   совпадающей с одним из 121 canonical Letteros-компонентов, — само по себе
   специфичный, воспроизводимый сигнал, а не наблюдение по одному файлу.

Поскольку шаг 2 полностью автоматический (без вопроса пользователю),
для его работоспособности нужен явный критерий: если в загруженном HTML не
найдено ни одного канонического UniSender-блока (п. 4.1), но сработал
сигнал 1 и/или 2 — письмо классифицируется как **Letteros**.

**`DECISION NEEDED`:** какой из двух сигналов использовать как критерий (или
оба, и в каком порядке/сочетании) — не решено этим документом. Разница
между ними: сигнал 1 не требует полного прохода `recognize_components()`
(дешевле), но менее строг и не гарантированно полон; сигнал 2 опирается на
реализованный и протестированный код, но может не сработать на письме,
собранном не из библиотечных компонентов вовсе (например, письмо из
Letteros, свёрстанное вручную, без единого библиотечного блока — тогда
формально это не ошибка классификации, а письмо действительно не содержит
известных компонентов). Выбор не меняет форму flow (результат всё равно один
из трёх дискретных исходов), но влияет на полноту охвата.

Ложноположительная классификация в обоих случаях маловероятна (оба сигнала
— специфичные совпадения, не общие паттерны); ложноотрицательная
(реальное Letteros-письмо не даёт сработать ни одному из сигналов) —
возможна, и в этом случае письмо попадёт в третью категорию (см. 4.3) и
будет остановлено с сообщением о неподдерживаемом формате, а не тихо
обработано неверно.

### 4.3. Всё остальное — неизвестный/третий формат

Если не сработал ни признак 4.1, ни признак 4.2 — формат не определён.
Поведение зафиксировано пользователем однозначно, без права додумывать:

- не импортировать;
- не пытаться угадывать соответствие компонентов;
- не делать частичную миграцию;
- сообщить, что формат не поддерживается, и остановить flow.

Пример сообщения:

> «Не удалось распознать формат этого письма как UniSender или Letteros.
> Такой формат пока не поддерживается — импортировать его нельзя.»

flow завершается здесь. Файл не возвращается, состояние очищается.

## 5. Ветка UniSender (сценарий A)

Реализуется полностью существующими и небольшими новыми переиспользуемыми
механизмами — минимально работоспособна уже сейчас, без разработки нового
подсистемного слоя.

### 5.1. Что происходит с письмом

Исходный HTML используется **как основа целиком**. Содержание и структура
письма (всё, кроме расписания) не разбираются на блоки и не проверяются на
соответствие библиотеке — они переносятся в результат без изменений,
вместе с исходным `<!DOCTYPE>`/`<head>`/остальной разметкой файла.
Единственная операция — заменить блок(и) расписания.

### 5.2. Шаг — запрос расписания

Бот запрашивает актуальное расписание сразу после того, как формат
определён как UniSender — без вопроса «нужно ли расписание» (в отличие от
предыдущей версии документа, где это было опционально): смысл этой функции
— обновить расписание в старом письме, поэтому шаг обязателен.

> «Пришлите файл `SCHEDULE.txt` с актуальным расписанием.»

Это тот же способ загрузки, что уже работает в «HTML-основа письма из
SCHEDULE.txt» и в «Генерация письма» (`handlers/generation.py`,
`ScheduleTxtFishStates.waiting_schedule_txt`).

Если у письма несколько допустимых визуальных вариантов расписания
(`Мероприятия/Расписание 1/2/3`) — бот показывает тот же выбор, что уже
есть в `ScheduleTxtFishStates.choosing_template`, без изменений.

### 5.3. Сборка блоков расписания — существующая цепочка, без изменений

```
SCHEDULE.txt  →  generation._parse_schedule_txt()  →  generation.build_schedule_blocks()
```

Как явно зафиксировано в `LEGACY_NEWSLETTER_MIGRATION.md`, раздел 4 — эту
цепочку менять не нужно, она переиспользуется как есть. Результат — список
готовых HTML-блоков расписания (один на календарную дату).

### 5.4. Замена расписания внутри целого письма — что нужно нового

Существующий близкий прецедент — `build_schedule_fish_html()`
(`generation.py:581-597`) — вставляет блоки расписания перед единственным
известным `</tbody>` в заранее подготовленной пустой оболочке
(`editor_templates/<branch>.html`). Для этой функции прецедент **не
подходит напрямую**: загруженное старое письмо — это уже полностью
собранный, произвольной структуры документ, а не пустая оболочка с одной
известной точкой вставки.

Нужна отдельная, небольшая по объёму операция (её нет в проекте сегодня):

1. Найти в загруженном HTML все блоки модуля `Мероприятия` — тем же
   механизмом, что и в п. 4.1, но с фильтром по модулю (переиспользуется
   `generation._scan_balanced_tr_end()` для определения точных границ
   каждого найденного блока).
2. Если такие блоки найдены — удалить их все и вставить новый список
   блоков расписания (п. 5.3) на месте первого удалённого.
3. Если блоков расписания в письме не было вовсе — найти блок модуля
   `Подвалы` (тем же механизмом) и вставить новые блоки расписания
   непосредственно перед ним — это соответствует установленному в проекте
   порядку блоков письма (материалы → расписание → подвал;
   `mail_project/README.md`, «Правила порядка блоков»;
   `mail_project/TEMPLATE_SPEC.md`, раздел «Расписание»).
4. Если не найдено ни блоков расписания, ни узнаваемого блока подвала —
   безопасной точки вставки нет. Функция не должна угадывать место
   вставки — это останавливающее условие (раздел 6).

Это точечная текстовая операция (найти границы → удалить/вставить
подстроку), не новый механизм сборки писем — не подменяет и не изменяет
существующую сборку компонентов.

### 5.5. Результат

Готовый HTML — это изменённый исходный документ (не новый документ,
собранный `build_email_html()` из списка блоков — эта функция здесь не
применяется, так как исходное письмо уже является полным документом со
своим `<head>`/стилями). Бот отправляет файл документом пользователю, тем
же способом, что и остальные операции подменю.

## 6. Ветка Letteros (сценарий B) — основной сценарий, статус реализации по этапам

### 6.1. Целевое поведение (требование)

1. Использовать старый HTML как исходник.
2. Автоматически распознать в нём известные canonical Letteros-компоненты
   (из `letteros_components.zip`).
3. Перенести содержимое (текст/ссылки/изображения) каждого распознанного
   фрагмента в одноимённый canonical UniSender-компонент, сохраняя
   содержание и визуальную структуру письма настолько, насколько это
   позволяет текущая каноническая библиотека.
4. Заменить расписание на актуальное — та же цепочка, что в разделе 5.3,
   без изменений.
5. Вернуть готовый HTML целиком.

Если фрагмент не удаётся надёжно сопоставить ни с одним компонентом
библиотеки — нельзя угадывать его тип (см. «Правило» во введении). Это
ошибка разбора конкретного письма, останавливающая его миграцию (раздел 7),
а не повод подобрать компонент «по смыслу» или молча пропустить содержимое.

### 6.2. Этап 1 (распознавание) — реализован

`mail_project/letteros_recognition.py`, покрыт тестами
`mail_project/test_letteros_recognition.py`. Алгоритм — два прохода:

1. Дешёвый поиск кандидатов по «подписи» обёртки компонента (align/
   bgcolor/background-color/padding/border-radius первого `<td>`, с
   нормализацией CSS shorthand и регистра hex-цвета) — переиспользует
   принцип, но не код `qa.find_components()` (в реальном экспортированном
   письме `letteros-element`/`letteros-module` не сохраняются — см.
   `LEGACY_NEWSLETTER_MIGRATION.md` §2.5).
2. Обязательная структурная проверка найденного кандидата целиком деревом
   тегов (адаптация принципа `qa.py`: сравнение по тегу и набору атрибутов,
   с допуском на отсутствующие `letteros-hide`-опциональные узлы, без учёта
   editor-only атрибутов Letteros и без сравнения текста/`src`/`href`,
   которые относятся к этапу 2). Найденный по «подписи» кандидат, не
   прошедший эту проверку, компонентом не считается.

Результат на полном прогоне всей библиотеки (letteros-атрибуты искусственно
сняты, чтобы имитировать реальный экспорт): 81 из 121 компонентов
распознаются однозначно; 40 из 121 корректно определяются как
принадлежащие известной, но неоднозначной без сравнения содержимого группе
(в основном семейства «шапка/подвал на филиал», отличающиеся только
логотипом/ссылкой) — не путаются с чужими и не теряются; 0 ошибочных или
потерянных результатов на всех 121 компонентах. На единственном реальном
Letteros-письме проекта (`mail_project/test/Копия — Копия — Футер Школа.html`)
итоговых подтверждений 0 (само письмо — не чистый HTTP-экспорт, а копия,
прошедшая через DOM браузера, что вносит искажения, которых не было бы в
чистом экспорте — см. `mail_project/test_letteros_recognition.py`,
класс `RealProjectLetterTests`), но поиск кандидатов корректно нашёл область
шапки и область подвала и сузил кандидатов до их истинных модулей.

### 6.3. Этап 2 (перенос содержимого) — не реализован

Не существует и не имитируется в рамках этой сессии:

- извлечение реального текста/ссылок/изображений из уже распознанного
  фрагмента (этап 1 сознательно их не читает — только подтверждает
  структурное соответствие фрагмента компоненту);
- устранение неоднозначности внутри 40 структурно-неразличимых
  компонентов — требует сравнения `href`/`src` найденного фрагмента с
  `href`/`src` каждого кандидата;
- подстановка извлечённых значений в соответствующий canonical
  UniSender-компонент — часть механизма для этого уже существует и
  переиспользуема (`build_generic_block()`, `_replace_text_once()`,
  `_replace_nth_href_hash()`, `_fill_first_local_image()`/
  `_fill_component_images()`), но вызывать её пока нечем — нет данных,
  извлечённых на предыдущем шаге;
- сборка итогового письма из результатов (`build_email_html()` — уже
  существует, готов быть переиспользован, когда появится список готовых
  блоков).

### 6.4. Что делает flow сегодня

Поскольку этап 2 не реализован, для письма, распознанного как Letteros
(раздел 4.2), функция **не может довести миграцию до готового HTML** — но
это не то же самое, что «формат не поддерживается» (раздел 4.3): формат
понятен и распознан, часть работы (этап 1) выполнена по-настоящему. Разница
существенна для пользователя: сообщение должно отражать реальный статус, а
не обобщённый отказ.

> «Это письмо из Letteros. Нашёл N известных блоков (и M фрагментов, которые
> не удалось однозначно определить). Автоматический перенос содержимого в
> готовое письмо UniSender для таких писем ещё не реализован.»

**`DECISION NEEDED`:** должен ли N/M (или сам факт частичного распознавания)
вообще показываться пользователю уже сегодня, до появления этапа 2 (как
статус разработки), или flow должен молчать про Letteros полностью, пока
результатом не станет готовый файл. Технической проблемы в показе статуса
нет (`recognize_components()` уже возвращает всё нужное для такого
сообщения) — вопрос в том, нужно ли это пользователю на данном этапе
готовности функции.

## 7. Где функция должна остановиться

1. **Загруженный файл не проходит базовую проверку** (не `.html`/`.htm`,
   пустой после декодирования) — просьба прислать файл заново или
   отменить.
2. **Формат определён как неизвестный/третий** (раздел 4.3) — жёсткая
   остановка, сообщение о неподдерживаемом формате, ничего не
   импортируется.
3. **Формат определён как Letteros, но этап 2 (перенос содержимого) ещё не
   реализован** (раздел 6.3–6.4) — остановка с сообщением о статусе
   разработки, не с сообщением «формат не поддерживается» (это разные
   сообщения — раздел 6.4).
4. **Фрагмент Letteros-письма не удалось однозначно сопоставить с
   canonical-компонентом** — ни разу (не найден даже кандидат «по подписи»),
   либо неоднозначно (несколько кандидатов прошли структурную проверку и
   различаются только содержимым, которое этап 1 не сравнивает, — раздел
   6.2). Не угадываем тип фрагмента — см. `DECISION NEEDED` ниже про то,
   останавливает ли это всю миграцию письма целиком или только этот
   фрагмент.
5. **Каноническая библиотека недоступна** (`manifest.json`/
   `unisender_components.zip`/`letteros_components.zip` отсутствуют или не
   проходят проверку Build Manager) — жёсткая остановка, аналог
   существующего `GenerationError`/`verify_build()`.
6. **В письме, распознанном как UniSender, не удалось найти безопасную
   точку вставки нового расписания** (ни старых блоков расписания, ни
   узнаваемого блока подвала — раздел 5.4, п.4) — остановка вместо
   угадывания места вставки.
7. **`SCHEDULE.txt` не прошёл разбор** (`_parse_schedule_txt()` поднимает
   ошибку — например, у события не хватает обязательных полей) —
   остановка, тот же принцип, что уже действует в `run()`/`run_selected()`/
   `build_schedule_fish()` сегодня.

Ни в одном из этих случаев бот не выдаёт частично собранный или
частично изменённый HTML.

## 8. Участие пользователя в flow

Это не покомпонентный набор решений (как в предыдущей версии), а всего два
возможных пользовательских действия во всём flow:

1. Загрузить файл старого письма (раздел 3).
2. Если формат — UniSender: загрузить `SCHEDULE.txt` и (если у выбранного
   компонента расписания есть несколько визуальных вариантов) выбрать
   вариант — оба шага переиспользуют уже существующие экраны бота
   (раздел 5.2).

Больше никаких решений о содержимом или структуре письма пользователь не
принимает. Всё остальное — определение формата, поиск и замена блоков
расписания, сборка результата — выполняется автоматически.

| # | Состояние (рабочее название) | Вход | Действие | Выход | Кто решает |
|---|---|---|---|---|---|
| 1 | `waiting_old_html` | нажатие кнопки запуска | бот просит файл | ожидание документа | — |
| 2 | приём файла | HTML-документ | проверка расширения/непустоты | принят / просьба повторить | система (проверка), пользователь (повтор) |
| 3 | `detecting_format` | текст HTML | автоматический поиск признаков UniSender (4.1) и Letteros (4.2) | один из трёх исходов: UniSender / Letteros / неизвестно | **система** (полностью автоматически, без вопроса) |
| 4a | UniSender → `waiting_schedule_txt` | факт «это UniSender» | бот просит `SCHEDULE.txt` | файл получен | пользователь загружает |
| 4b | Letteros → распознавание | факт «это Letteros» | `letteros_recognition.recognize_components()` (реализовано) | список распознанных/нераспознанных фрагментов | система (авто) |

| 5 | `choosing_schedule_template` (если применимо) | список вариантов расписания | бот показывает варианты (как в `ScheduleTxtFishStates`) | вариант выбран | пользователь |

| 8 | выдача результата | изменённый HTML | бот отправляет файл документом | файл у пользователя, состояние очищено | — |

## 10. `DECISION NEEDED`

Только вопросы, которые действительно не решены существующими файлами
проекта и влияют на конкретное поведение конкретного шага.

### DECISION NEEDED 1 — Маркер распознавания «старое письмо уже из UniSender»

Не изменилось относительно предыдущей версии документа. Автоматический
разбор (раздел 4.1) должен на что-то опираться при поиске канонических
блоков в произвольном HTML. Сегодняшний код (`qa.find_components()`) ищет
пару `letteros-element`/`letteros-module`, не проверяя `em="block"`. Не
решено (унаследовано из `LEGACY_NEWSLETTER_MIGRATION.md`, раздел 1.2),
должна ли новая функция полагаться на тот же признак, на `em="block"`, или
на оба одновременно.

### DECISION NEEDED 2 — Источник канонической библиотеки для этой функции

В проекте есть два разных прецедента, откуда брать `manifest.json`/
`unisender_components.zip` для операции: «Проверка качества письма» берёт
их напрямую из текущего состояния `mail_project/` (без `BUILD_ID`,
`qa.run_standalone()`); «HTML-основа письма из SCHEDULE.txt» создаёт новый
`BUILD_ID` только ради доступа к замороженному снимку библиотеки
(`gensvc.create_build()` + `build_schedule_fish()`). Эта функция строит
новые блоки расписания (`build_schedule_blocks()`), что по характеру
операции ближе ко второму прецеденту, но однозначно унаследованного
решения нет ни в одном документе. На форму flow (шаги, вход/выход) это не
влияет — оба варианта дают пользователю одинаковый результат и одинаковый
диалог. То же касается и `letteros_components.zip`: сегодня
`letteros_recognition.load_letteros_library()` читает его напрямую из
`mail_project/`, без привязки к `BUILD_ID` — вопрос, нужен ли ему тот же
снимок-через-Build-Manager, что и остальным двум файлам, не решён здесь же.

### DECISION NEEDED 3 — Сигнал(ы) для классификации формата как Letteros

Дублирует вопрос из раздела 4.2 (вынесен сюда для полноты списка): признаки-
строки (`LEGACY_NEWSLETTER_MIGRATION.md` §2.2) против совпадения кандидата в
`recognize_components()` (раздел 6.2) — какой использовать как критерий,
не решено. Не меняет форму flow.

### DECISION NEEDED 4 — Останавливать всю миграцию письма или только нераспознанный фрагмент

Когда `recognize_components()` возвращает нераспознанный фрагмент (раздел
7, п.4) — не решено, должно ли это немедленно останавливать весь разбор
письма (первый же нераспознанный фрагмент — стоп), или собирать все
нераспознанные фрагменты, продолжая разбор остальных, и показать
пользователю сводный список после полного прохода письма (по аналогии с
тем, как уже устроен `qa._check_and_fix()` — один заблокированный компонент
не останавливает проверку остальных, но итоговый статус письма становится
`BLOCKED`). Технически `RecognitionResult` из
`mail_project/letteros_recognition.py` уже устроен под второй вариант
(копит `unresolved` и продолжает сканирование) — но использовать ли это
поведение как окончательное для остановки всей функции, а не только этапа
распознавания, не решено.
