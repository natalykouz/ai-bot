# GENERATION_RULES.md

## Назначение

Этот документ определяет алгоритм production-сборки HTML email-рассылки
из входного промпта SMM.

Генератор собирает письмо только из актуальной канонической библиотеки
компонентов.

Генератор не придумывает структуру письма и не создаёт новые визуальные
компоненты.

Главный принцип:

> Канонический компонент является готовым HTML-фрагментом.
> При сборке в него подставляются только предусмотренные компонентом данные.
> HTML-структура, CSS, типографика, таблицы, колонки и responsive-механика
> компонента не пересобираются.

---

## 1. Источники production-сборки

Использовать только актуальные файлы проекта и данные текущего выпуска.

### Разрешённые источники

- `TEMPLATE_SPEC.md` — структура письма и ограничения;
- `CONTENT_SCHEMA.md` — структура входных данных;
- `manifest.json` — актуальный каталог компонентов;
- актуальная библиотека `unisender_components` — канонический HTML
  компонентов;
- `MGI_UNISENDER_ASSETS.md` — постоянные системные assets МГИ;
- `IMAGE_SLOTS.md` — правила переменных image-slot'ов;
- `UTM.md` — правила формирования UTM;
- `SCHEDULE.txt` — готовые данные расписания текущего выпуска, если
  расписание используется;
- контент, явно переданный SMM в текущем промпте;
- другие явно приложенные файлы текущего выпуска, если они необходимы
  для конкретного блока.

`GENERATION_RULES.md` определяет алгоритм сборки и не является источником
контента текущей рассылки.

### Ограничение источников

Для production-сборки запрещено использовать:

- исторические HTML-письма;
- `.eml`;
- `index.html`;
- архивные компоненты;
- старые версии компонентов;
- старые выгрузки мероприятий;
- исторические изображения;
- архивные справочники;
- ранее созданные рассылки;
- старые версии проектных документов;
- ранее проиндексированные версии файлов;
- любые другие исторические материалы проекта.

Если актуальный источник недоступен или не читается, не заменять его
старой или ранее проиндексированной версией.

Исторические материалы не используются для восстановления структуры,
контента или визуального оформления текущей рассылки.

## 2. Анализ входного промпта

Из промпта SMM определить:

- филиал;
- тему рассылки;
- последовательность блоков;
- содержание каждого блока;
- указанное SMM название компонента, если оно есть;
- ссылки;
- наличие расписания;
- период расписания;
- приложенные данные текущего выпуска;
- дополнительные требования к выпуску.

Сначала определить логическую структуру письма и порядок блоков.

Затем для каждого блока определить подходящий компонент из актуальной
библиотеки и необходимые данные для его заполнения.

Не добавлять блоки, которых нет во входных данных или обязательной
структуре проекта.

Не удалять обязательные системные блоки.

---

## 3. Выбор компонентов

Все компоненты выбираются только из актуального `manifest.json` и
соответствующей актуальной библиотеки `unisender_components`.

### 3.1. Точное соответствие

Если название компонента из промпта SMM точно соответствует компоненту
в актуальном `manifest.json`, использовать именно этот компонент.

### 3.2. Неточное название

Название компонента в промпте SMM не обязано дословно совпадать с названием
в `manifest.json`.

Если указанное название неточное, но по смыслу однозначно понятно, какой
тип блока требуется, выбрать из актуальной библиотеки наиболее близкий
компонент.

При выборе учитывать:

- назначение блока;
- тип контента;
- визуальную функцию;
- количество и тип элементов;
- наличие изображения;
- наличие кнопки;
- структуру карточки;
- особенности размещения контента;
- соответствие компонента месту блока в письме.

Например, если SMM называет блок `Hero`, а в актуальном каталоге нет
раздела `Hero`, но есть подходящий компонент в разделе `Баннеры`, следует
выбрать наиболее близкий по назначению компонент `Баннеры`, а не
останавливать сборку из-за несовпадения названия.

### 3.3. Приоритет явного выбора

Если SMM указал компонент достаточно однозначно, не заменять его без
необходимости.

Если название компонента неточное, допускается выбрать другой компонент
только для устранения несоответствия названия реальному каталогу.

Нельзя использовать гибкость выбора для произвольной замены компонента
на более удобный или визуально привлекательный.

### 3.4. Неоднозначный выбор

Если по смыслу нельзя однозначно определить подходящий компонент,
не придумывать компонент и не создавать новый.

В таком случае сообщить, какой блок невозможно однозначно сопоставить
с актуальной библиотекой.

### 3.5. Запрещено

Нельзя:

- придумывать название компонента;
- использовать компонент, которого нет в актуальном `manifest.json`;
- восстанавливать компонент по старому HTML;
- выбирать компонент из исторической версии библиотеки;
- создавать новый визуальный компонент;
- собирать блок вручную вместо существующего подходящего компонента;
- использовать только визуальное сходство как основание для выбора,
  если назначение компонента другое.

---

## 4. Сборка из канонических компонентов

Каждый выбранный компонент берётся из актуальной библиотеки как готовый
HTML-фрагмент.

При сборке изменяются только предусмотренные компонентом значения:

- текст;
- ссылки;
- данные повторяемых элементов;
- предусмотренные image-slot'ы;
- другие явно предусмотренные компонентом переменные значения.

Исходная HTML-структура компонента сохраняется.

Канонический компонент нельзя:

- переписывать;
- собирать заново по визуальному виду;
- реконструировать по памяти;
- заменять структурой другого компонента;
- упрощать;
- перестраивать под конкретный текст;
- дополнять собственными внутренними контейнерами.

Если контент длиннее или короче ожидаемого, не менять структуру компонента
для подгонки контента.

---

## 5. CSS и responsive

CSS является частью канонического компонента и должен сохраняться
без изменений.

При сборке нельзя изменять или добавлять:

- inline CSS;
- `<style>`;
- media queries;
- font-family;
- font-size;
- font-weight;
- line-height;
- letter-spacing;
- цвета;
- ширины;
- высоты;
- отступы;
- padding;
- границы;
- радиусы;
- выравнивание;
- колонки;
- таблицы;
- responsive-механику.

Нельзя добавлять глобальный CSS.

Нельзя добавлять собственные responsive-правила.

Нельзя оптимизировать или упрощать CSS компонента.

Нельзя менять CSS для исправления визуального поведения конкретного
контента.

Если компонент корректно работает на desktop и mobile в канонической
версии, его responsive-структура должна быть сохранена полностью.

---

## 6. Повторение компонентов

Если один компонент используется несколько раз, каждый экземпляр
создаётся из полной структуры исходного компонента.

Экземпляры:

- находятся на одном уровне структуры письма;
- не вкладываются друг в друга;
- не объединяются в самодельную структуру;
- не переносят HTML или контент друг между другом.

Нельзя создавать новый экземпляр копированием только внутренней части
компонента.

Для повторяемых компонентов image-slot'ы должны иметь уникальные
`slot_id`.

---

## 7. Текст и контент

Содержательный контент текущего выпуска берётся только из разрешённых
источников текущего выпуска.

Не придумывать:

- названия;
- даты;
- время;
- описания;
- имена;
- мероприятия;
- ссылки;
- изображения;
- дополнительные смысловые блоки.

Не переносить содержательный текст из примеров компонентов.

Не заменять отсутствующие данные догадками.

### HTML в текстовых значениях

Текстовые данные и HTML-структура компонента должны оставаться
разделёнными.

В текстовые значения не вставлять HTML-теги.

Если компонент предусматривает отдельные абзацы, строки или другие элементы,
использовать предусмотренную компонентом структуру.

Не создавать HTML-разметку внутри передаваемого текстового значения.

---

## 8. Ссылки и UTM

Не придумывать URL.

Ссылка должна относиться к соответствующему материалу или событию.

UTM применять согласно `UTM.md`.

Если в промпте SMM уже указана корректная ссылка с UTM, не изменять её
без необходимости.

Не переносить UTM другого подразделения или другого объекта.

---

## 9. Расписание

Если расписание включено, использовать `SCHEDULE.txt` текущего выпуска.

`SCHEDULE.txt` содержит готовые данные для сборки расписания.

Не использовать исторические выгрузки мероприятий.

Не придумывать мероприятия, даты, время или другие данные расписания.

Не изменять содержательные данные событий при переносе их в компонент
Schedule.

Каждая календарная дата оформляется согласно структуре канонического
компонента Schedule.

Если расписание содержит несколько дат, каждая дата оформляется отдельным
экземпляром канонического Schedule.

Экземпляры Schedule разных дат должны находиться последовательно и на
одном уровне структуры письма.

Schedule не должен содержать внутри себя:

- другой Schedule;
- Footer;
- Header;
- другие компоненты письма.

При повторении Schedule сохранять полную каноническую структуру компонента.

Количество строк событий должно соответствовать данным `SCHEDULE.txt`.

Не создавать:

- пустые строки;
- пустые даты;
- дополнительные секции той же даты;
- объединённые вручную даты;
- вложенные Schedule.

---

## 10. Изображения

Изображения разделяются на:

1. системные assets;
2. переменные изображения текущего выпуска.

### Системные assets

Постоянные системные assets брать из актуальной канонической библиотеки
и `MGI_UNISENDER_ASSETS.md`.

Не заменять их случайными изображениями.

Не удалять их при сборке.

### Переменные image-slot'ы

Для каждого выбранного компонента определить предусмотренные им
переменные image-slot'ы.

Правила их обработки определяются `IMAGE_SLOTS.md`.

Если изображение для slot отсутствует:

- не останавливать генерацию;
- не менять структуру компонента;
- использовать предусмотренный технический placeholder;
- сохранить `slot_id`;
- сохранить предусмотренный компонентом размер и структуру slot;
- указать содержательный `alt` для будущего изображения.

Placeholder является значением `src` существующего image-slot.

Не создавать отдельный элемент или контейнер для placeholder.

Подготовка или замена реальных изображений не является отдельным этапом
генерации.

После генерации HTML работа с реальными изображениями выполняется
вне сборки HTML и не требует повторной генерации письма.

---

## 11. Неполные данные

Сначала проверить все разрешённые актуальные источники.

Если обязательное содержательное значение отсутствует и его нельзя
однозначно получить из разрешённых источников:

- не придумывать значение;
- не брать значение другого объекта;
- не использовать исторические материалы;
- не использовать ранее проиндексированную версию;
- не заменять отсутствие данных фиктивным содержательным текстом.

Если отсутствие данных не позволяет корректно собрать блок, сообщить
о конкретно отсутствующем значении.

Отсутствие переменного изображения не является блокером: для него
используется предусмотренный placeholder.

---

## 12. Финальная проверка перед выдачей HTML

Перед выдачей HTML проверить:

1. структура письма соответствует `TEMPLATE_SPEC.md`;
2. каждый выбранный компонент существует в актуальном `manifest.json`;
3. для каждого блока выбран существующий канонический компонент;
4. если название компонента SMM было неточным, выбран ближайший по смыслу
   существующий компонент;
5. порядок блоков соответствует входным данным;
6. обязательные содержательные данные присутствуют;
7. ссылки относятся к правильным объектам;
8. UTM применены согласно `UTM.md`;
9. если используется расписание, данные взяты из `SCHEDULE.txt`;
10. Schedule не вложен в другой Schedule или другой компонент;
11. повторяемые компоненты не вложены друг в друга;
12. системные assets сохранены;
13. отсутствующие переменные изображения имеют предусмотренные
    placeholder'ы;
14. placeholder'ы имеют уникальные `slot_id`;
15. HTML-структура канонических компонентов не пересобрана;
16. CSS канонических компонентов не изменён;
17. responsive-структура канонических компонентов не изменена;
18. в текстовые значения не вставлены HTML-теги;
19. в письмо не добавлены блоки, которых нет во входных данных или
    обязательной структуре проекта;
20. в HTML не попали данные из исторических или неактуальных источников.

Если эти условия не выполнены, HTML не считать готовым.

---

## 13. Результат

Результатом этапа генерации является:

**полный HTML письма**, собранный из актуальных канонических компонентов.

HTML должен содержать:

- все предусмотренные блоки;
- каноническую HTML-структуру компонентов;
- канонический CSS;
- каноническую responsive-механику;
- системные assets;
- предусмотренные image-slot placeholder'ы при отсутствии реальных
  изображений.

Отдельный этап подготовки изображений в результат генерации не входит.

После генерации HTML письмо передаётся на отдельный этап технического QA.

---

## 14. Категорически запрещено

Нельзя:

- придумывать мероприятия;
- придумывать ссылки;
- придумывать даты и время;
- придумывать изображения;
- использовать исторические или неактуальные источники;
- использовать ранее проиндексированные версии файлов вместо актуальных;
- восстанавливать текущий файл по старой версии;
- создавать новые визуальные компоненты;
- использовать компонент, отсутствующий в актуальном `manifest.json`;
- реконструировать компонент по памяти или визуальному виду;
- изменять каноническую HTML-структуру;
- изменять CSS;
- изменять responsive-механику;
- добавлять глобальный CSS;
- создавать собственные media queries;
- вкладывать один экземпляр компонента в другой;
- вкладывать Schedule в Schedule;
- вкладывать Footer в Schedule;
- заменять Schedule самодельной разметкой;
- создавать пустые даты или строки расписания;
- переносить данные одного события в другое;
- создавать дополнительные блоки без основания во входных данных или
  обязательной структуре проекта;
- вставлять HTML-теги в текстовые значения;
- заменять отсутствующий image-slot обычным текстом;
- использовать исторические image placeholder'ы;
- останавливать генерацию из-за отсутствия переменного изображения;
- добавлять к результату несуществующие или вымышленные компоненты.
