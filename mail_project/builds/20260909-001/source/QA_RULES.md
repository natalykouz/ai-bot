# QA_RULES.md

## Назначение

Этот документ определяет правила технической QA-проверки готового HTML
email после этапа Generation.

QA проверяет не содержание и не структуру рассылки как контентного объекта,
а соответствие вёрстки использованных компонентов их каноническим HTML.

Главный принцип

 QA сравнивает готовый HTML с каноническим HTML соответствующих компонентов
 и точечно исправляет обнаруженные дефекты вёрстки.

QA не пересобирает письмо.

---

## 1. Источники

Для QA используются только

- готовый HTML проверяемого письма;
- актуальный HTML соответствующих компонентов из `unisender_components`;
- актуальный `manifest.json` — только для идентификации компонентов;
- `IMAGE_SLOTS.md` — только для проверки image-slot;
- `MGI_UNISENDER_ASSETS.md` — только для проверки системных assets.

Не использовать

- `GENERATION_RULES.md`;
- исторические HTML;
- `.eml`;
- архивные компоненты;
- старые версии компонентов;
- старые версии проектных документов;
- ранее созданные рассылки.

Если канонический HTML компонента недоступен в актуальной библиотеке,
не восстанавливать его по старой версии.

---

## 2. Объект проверки

Проверяется каждый использованный компонент готового письма.

Для каждого компонента сравниваются

- HTML-структура;
- таблицы;
- строки;
- ячейки;
- вложенность;
- inline CSS;
- CSS в `style`;
- media queries;
- шрифты;
- размеры;
- ширины;
- высоты;
- отступы;
- выравнивание;
- изображения;
- позиционирование изображений;
- responsive-поведение.

Канонический HTML компонента является эталоном.

---

## 3. Что проверять

### HTML-вёрстка

Проверить, что

- структура компонента сохранена;
- таблицы не изменены без необходимости;
- строки и ячейки находятся на правильном уровне;
- вложенность соответствует канону;
- закрывающие теги находятся на правильном уровне;
- один компонент не оказался вложен в другой;
- не появились лишние контейнеры;
- не исчезли обязательные элементы компонента.

Особенно проверять повторяемые компоненты

- карточки;
- Schedule;
- баннеры;
- контентные блоки.

---

## 4. CSS

Сравнить CSS готового компонента с каноническим HTML.

Проверить

- `font-family`;
- `font-size`;
- `font-weight`;
- `line-height`;
- `letter-spacing`;
- `color`;
- `background`;
- `width`;
- `max-width`;
- `height`;
- `padding`;
- `margin`;
- `text-align`;
- `vertical-align`;
- `display`;
- другие свойства, присутствующие в каноническом компоненте.

Если свойство канонического компонента было изменено без необходимости,
восстановить каноническое значение.

Не переписывать CSS целиком, если дефект можно исправить точечно.

---

## 5. Шрифты

Проверить соответствие шрифтов каноническому компоненту.

Отдельно проверять

- семейство шрифта;
- размер;
- начертание;
- межстрочный интервал;
- letter-spacing.

Проверять типографику всех элементов, для которых она задана компонентом.

Особое внимание

- заголовкам;
- датам;
- времени;
- CTA;
- основному тексту;
- подписям.

Контент не должен приводить к изменению типографики компонента.

---

## 6. Responsive

Проверить, что responsive-вёрстка полностью сохранена из канонического
компонента.

Проверить

- мобильную ширину;
- ширину основного контейнера;
- максимальную ширину;
- переход колонок;
- размеры элементов на мобильном;
- размеры изображений;
- отступы;
- media queries;
- скрытие и отображение элементов;
- отсутствие фиксированной ширины, ломающей мобильное отображение.

Если мобильная версия отличается от канонической, восстановить
каноническую responsive-структуру.

Не проектировать новую responsive-вёрстку.

---

## 7. Изображения

Проверить соответствие изображения каноническому image-slot

- положение;
- размеры;
- ширину;
- высоту;
- пропорции;
- способ размещения;
- CSS;
- наличие предусмотренного `alt`.

Не менять способ размещения изображения

- `img` не заменять на `background-image`;
- `background-image` не заменять на `img`.

Не создавать дополнительные изображения.

Количество image-slot'ов определяется каноническим HTML компонента,
а не количеством случайно обнаруженных URL или изображений.

---

## 8. Image-slot

Для переменных изображений использовать `IMAGE_SLOTS.md`.

Проверить

- image-slot находится в правильном месте;
- структура slot соответствует каноническому компоненту;
- `slot_id` не потерян;
- placeholder не заменён на другой технический asset;
- `alt` сохранён;
- размеры slot не изменены;
- CSS slot не изменён.

При отсутствии реального изображения допустим placeholder,
предусмотренный `IMAGE_SLOTS.md`.

QA не должен создавать новый image-slot.

---

## 9. Системные assets

Проверить сохранность системных assets,
предусмотренных каноническим компонентом

- логотипов;
- стрелок;
- иконок;
- элементов Schedule;
- других постоянных изображений компонента.

Сверять их с `MGI_UNISENDER_ASSETS.md`.

Если системный asset пропал или был заменён,
восстановить его из актуального канонического источника.

Не заменять системный asset placeholder'ом.

---

## 10. Вложенность компонентов

Компоненты должны оставаться самостоятельными экземплярами.

Нельзя допускать вложенность, которой нет в каноническом HTML.

Особенно проверить

- Schedule внутри Schedule;
- один экземпляр карточного компонента внутри другого;
- один баннер внутри другого компонента;
- случайно вложенные таблицы;
- элементы следующего компонента внутри предыдущего.

При обнаружении неправильной вложенности восстановить структуру
по каноническому HTML.

---

## 11. Schedule

Если Schedule присутствует в письме, проверять только его вёрстку.

Проверить

- структуру таблиц;
- вложенность;
- типографику;
- шрифт времени;
- размер времени;
- начертание времени;
- размеры и отступы;
- структуру даты;
- структуру названия;
- структуру ссылки;
- responsive-поведение.

Каждый экземпляр Schedule должен иметь самостоятельную структуру,
соответствующую каноническому компоненту.

Schedule не должен содержать другой Schedule или другой компонент.

---

## 12. Что QA не проверяет

QA не проверяет

- правильность содержания письма;
- редактуру текста;
- порядок контентных блоков;
- наличие или отсутствие блоков;
- выбор компонентов;
- соответствие темы содержанию;
- корректность мероприятий;
- корректность расписания как набора данных;
- URL и UTM;
- полноту контента;
- маркетинговую логику;
- смысловую корректность рассылки.

Если проблема относится к этим областям, QA не должен исправлять её
самостоятельно.

---

## 13. Что QA не делает

QA не

- выбирает другой компонент;
- добавляет новый компонент;
- удаляет компонент;
- пересобирает письмо;
- переписывает HTML всего письма;
- меняет дизайн;
- создаёт новую CSS-систему;
- придумывает responsive-решение;
- меняет контент;
- заменяет изображения на другие;
- создаёт отсутствующие assets.

---

## 14. Точечное исправление

При обнаружении дефекта

1. определить конкретный компонент;
2. найти соответствующий канонический HTML;
3. определить минимальный дефектный участок;
4. сравнить его с каноном;
5. восстановить только дефектный участок;
6. не изменять корректные соседние элементы;
7. повторно проверить компонент после исправления.

Приоритет имеет минимальное изменение.

---

## 15. Проверка после исправлений

После всех исправлений повторно проверить

- HTML-структуру компонента;
- вложенность;
- CSS;
- шрифты;
- размеры;
- отступы;
- изображения;
- image-slot'ы;
- системные assets;
- responsive.

Особенно убедиться, что точечное исправление одного компонента
не изменило соседний компонент или общую структуру письма.

---

## 16. Результат QA

QA должен выдать

1. полный исправленный HTML;
2. краткий список технических исправлений.

Если дефектов не обнаружено

- не изменять HTML;
- вернуть исходный HTML;
- указать, что технических дефектов не обнаружено.

QA не должен выдавать новую версию структуры письма.

---

## 17. Критический принцип

Канонический HTML компонента — единственный эталон его вёрстки.

Если готовый HTML отличается от канонического компонента,
QA исправляет отличие, если оно относится к вёрстке, CSS, типографике,
изображению или responsive-поведению.

Если проблема не относится к технической вёрстке компонента,
QA её не исправляет.
