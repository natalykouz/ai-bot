# IMAGE_SLOTS.md

## Назначение

Этот документ определяет правила работы с переменными изображениями
(image-slot'ами) в production HTML-рассылках.

Image-slot — это существующий в каноническом HTML-компоненте элемент
изображения, содержимое которого зависит от конкретного выпуска.

Image-slot не создаёт новую структуру письма. При сборке используется
существующий image-slot выбранного компонента.

---

## 1. Источники

Правила image-slot определяются только по актуальным:

- `manifest.json`;
- HTML выбранного компонента из актуальной библиотеки;
- `MGI_UNISENDER_ASSETS.md`;
- данным текущего выпуска;
- контексту блока из промпта SMM.

Не использовать исторические HTML, `.eml`, архивные компоненты,
старые выгрузки или ранее проиндексированные версии файлов.

Если актуальный компонент недоступен, его image-slot нельзя восстанавливать
по старой версии или по памяти.

---

## 2. Два типа изображений

### 2.1. Системные assets

Системные assets являются частью канонической библиотеки.

К ним относятся, в частности:

- логотипы;
- стрелки;
- иконки;
- элементы Schedule;
- изображения Footer;
- другие неизменяемые изображения компонентов.

Они берутся из актуального компонента и/или
`MGI_UNISENDER_ASSETS.md`.

Системный asset не является image-slot'ом текущего выпуска.

Его нельзя:

- заменять placeholder'ом;
- заменять случайным изображением;
- удалять из компонента;
- включать в список изображений для подготовки SMM.

### 2.2. Переменные изображения

Переменное изображение относится к конкретному выпуску и заменяется
в существующем image-slot выбранного компонента.

Переменные image-slot'ы определяются только после выбора компонентов.

---

## 3. Определение image-slot'ов

После выбора всех компонентов генератор должен определить все
переменные image-slot'ы, присутствующие в используемых экземплярах
компонентов.

Для каждого image-slot:

1. определить его в исходном HTML компонента;
2. определить соответствующий variable image в `manifest.json`;
3. определить назначение изображения из структуры компонента;
4. создать уникальный `slot_id` для конкретного экземпляра;
5. сохранить исходную структуру image-slot;
6. определить требования к изображению по компоненту.

Один image-slot соответствует одному конкретному изображению.

Если один и тот же компонент используется несколько раз, image-slot'ы
в разных экземплярах получают разные `slot_id`.

---

## 4. Идентификатор slot

`slot_id` должен быть уникальным внутри всего письма.

Формат технического маркера отсутствующего изображения:

`IMAGE_MISSING_<slot_id>`

Пример:

`IMAGE_MISSING_hero_01`

Идентификатор должен однозначно позволять связать:

- image-slot в HTML;
- изображение;
- описание изображения;
- конкретный блок письма.

Не использовать один `slot_id` для разных изображений.

---

## 5. Отсутствующее изображение

Если фактического изображения текущего выпуска нет, генерация HTML
не блокируется.

В `src` существующего image-slot используется маркер:

`IMAGE_MISSING_<slot_id>`

Маркер заменяет только значение `src`.

Не создавать из-за отсутствующего изображения:

- новый `<img>`;
- новый контейнер;
- дополнительную таблицу;
- дополнительную высоту;
- отдельный блок;
- другую HTML-структуру.

Исходная структура компонента должна остаться неизменной.

---

## 6. Placeholder asset

Для production используется универсальный технический placeholder:

`6fea2cfd-955f-4aab-89d6-c3cb52deb89f.png`

Он указан в актуальном `MGI_UNISENDER_ASSETS.md` как технический
placeholder для переменных image-slot'ов. :contentReference[oaicite:0]{index=0}

Placeholder не является контентным изображением.

Его исходный размер файла не определяет размер image-slot.

Размер изображения в HTML должен соответствовать требованиям
конкретного image-slot выбранного компонента. :contentReference[oaicite:1]{index=1}

---

## 7. Как используется placeholder

В production HTML одновременно сохраняются:

- существующий image-slot;
- его исходные размеры и параметры;
- технический placeholder asset;
- уникальный `slot_id`;
- содержательный `alt`.

Placeholder занимает место будущего изображения, но не меняет
геометрию компонента.

После подготовки реального изображения SMM заменяет placeholder
на URL изображения в том же image-slot.

Повторная сборка письма из-за замены изображения не требуется.

---

## 8. Alt

Каждый переменный image-slot должен иметь содержательный `alt`.

`alt` описывает изображение, которое должно находиться в данном slot.

Описание определяется по:

1. контексту блока;
2. содержанию текущего промпта SMM;
3. назначению image-slot в компоненте.

Не придумывать конкретные визуальные детали, которых нет
в исходных данных.

Не использовать в качестве `alt`:

- `IMAGE_MISSING_<slot_id>`;
- UUID placeholder asset;
- название компонента;
- техническое название slot;
- бессмысленные значения вроде `image`, `photo`, `picture`.

---

## 9. Требования к размеру и пропорциям

Размер, пропорция и способ отображения изображения определяются
выбранным компонентом.

Не придумывать:

- ширину;
- высоту;
- пропорцию;
- crop;
- safe area;
- позиционирование;
- `object-fit`;
- `background-size`.

Если компонент содержит соответствующие параметры, они сохраняются
без изменений.

Исходный размер placeholder asset не используется для определения
размера slot.

---

## 10. `<img>` и background-image

Нельзя заменять один способ размещения изображения другим.

Если канонический компонент использует `<img>`, сохраняется `<img>`.

Если канонический компонент использует фоновое изображение,
сохраняется фоновое изображение.

Нельзя переносить изображение из `background-image` в `<img>` или
наоборот.

Нельзя создавать дополнительный `<img>` поверх существующего
background-image.

---

## 11. Компоненты с несколькими image-slot'ами

Если компонент содержит несколько переменных изображений, каждое
из них является отдельным image-slot.

Каждый slot получает:

- собственный `slot_id`;
- собственный placeholder;
- собственный `alt`;
- собственную запись в списке изображений.

Например, компонент с четырьмя переменными изображениями имеет четыре
image-slot'а, если все четыре изображения действительно являются
переменными.

Наличие четырёх image variables в `manifest.json` само по себе не означает,
что генератор должен создавать дополнительные изображения: используется
ровно та структура, которая присутствует в выбранном HTML-компоненте.

Актуальный `manifest.json`, например, содержит компонент
`Изображения / Четыре изображения` с четырьмя отдельными image variables. :contentReference[oaicite:2]{index=2}

---

## 12. Повторяемые компоненты

Если компонент с image-slot используется несколько раз:

- каждый экземпляр сохраняет полную исходную структуру;
- image-slot'ы разных экземпляров не объединяются;
- каждый slot получает уникальный `slot_id`;
- изображения одного экземпляра не переносятся в другой.

Не использовать один placeholder или один `slot_id` для нескольких
экземпляров.

---

## 13. Список изображений для SMM

После сборки генератор формирует список переменных изображений текущего
выпуска.

Для каждого изображения указать:

- `slot_id`;
- блок письма;
- назначение изображения;
- требования к изображению, если они явно определены компонентом.

В список включаются только переменные изображения.

Не включаются:

- логотипы;
- стрелки;
- иконки;
- системные изображения;
- Footer;
- другие постоянные assets.

---

## 14. Замена изображения после генерации

При подготовке изображения SMM не должен менять HTML-структуру компонента.

Заменяется только содержимое соответствующего image-slot:

- placeholder `src` → реальный URL изображения;
- `alt` остаётся содержательным описанием изображения.

Не изменять при замене изображения:

- размеры slot;
- CSS;
- таблицы;
- контейнеры;
- колонки;
- responsive-структуру;
- соседние элементы компонента.

---

## 15. Критические инварианты

Для каждого переменного изображения должно выполняться:

`1 image-slot = 1 изображение = 1 slot_id`

Для каждого отсутствующего изображения:

`существующий image-slot + placeholder + уникальный slot_id + содержательный alt`

Нельзя:

- создавать image-slot вне компонента;
- удалять существующий image-slot;
- менять структуру компонента ради изображения;
- заменять системный asset placeholder'ом;
- использовать исторический placeholder вместо production placeholder;
- придумывать параметры изображения, которых нет в каноническом компоненте.
