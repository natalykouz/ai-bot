# COMPONENT_INPUT_MODEL.md

Фиксация текущего (фактического) поведения flow «Генерация письма» в Telegram-боте.
Источники — только код проекта на момент анализа: `handlers/generation.py`,
`services/generation_service.py`, `mail_project/generation.py`, `mail_project/manifest.json`,
`mail_project/IMAGE_SLOTS.md`, а также фактический результат одной из существующих сборок
(`mail_project/builds/20260904-007`) — использован как проверка кода на реальных данных,
а не как источник новых утверждений.

Код и логика не менялись.

---

## 1. Как менеджер сейчас выбирает компонент

Flow: `Email-рассылки` → `Генерация письма` (`handlers/generation.py`, класс `LetterGenStates`).

Порядок шагов:

1. Филиал (`choose_branch`).
2. Использовать расписание — да/нет (если да, нужен готовый `SCHEDULE.txt`, Schedule processor в этом flow не запускается).
3. **Шапка** — компонент выбирается из списка `gensvc.header_options(branch)` (module `"Шапки"`, отфильтровано по филиалу). Если для филиала компонента нет — шаг молча пропускается.
4. **Баннеры (Hero)** — выбор из `gensvc.hero_options()` (все элементы module `"Баннеры"`). Обязательный шаг.
5. **Подвалы (Footer)** — выбор из `gensvc.footer_options(branch)`. Обязательный; если для филиала компонента нет — генерация дальше невозможна.
6. **Контентные компоненты** (цикл, 0..N раз) — сначала модуль из фиксированного списка `gensvc.CONTENT_MODULES` (`Баннеры`, `Дополнительные Баннеры`, `Изображения`, `Текстовые блоки`, `Кнопки`, `Разделители`, `Авторы`, `Большие контентные блоки`, `Контентные блоки`), затем конкретный элемент модуля из `gensvc.content_elements(module)`.

Все списки для выбора — это фактические `module`/`element` из `mail_project/manifest.json` (122 записи, 12 модулей), без какой-либо дополнительной фильтрации по смыслу или полноте данных о компоненте.

## 2. Что бот просит ввести

После выбора конкретного контентного компонента (`choose_content_element`, `handlers/generation.py:375-395`):

```
count = gensvc.sample_text_count(module, element)
```

`sample_text_count()` (`services/generation_service.py:95-99`) возвращает **длину массива `sample_text` этого компонента в `manifest.json`** — и ничего больше.

- Если `count == 0` — бот вообще не просит текст, компонент сразу добавляется как есть.
- Если `count > 0` — бот пишет: *«Введите содержимое компонента — N строк, каждая с новой строки»* и ждёт одно текстовое сообщение, где строки разделены `\n`. Проверяется только **количество** строк (`len(lines) != count` → отказ); пустые строки, длина и формат не проверяются.

Для Header и Footer текст не запрашивается вообще (см. п.4).

---

## 3. Что означает каждая строка

Строка `i` = `sample_text[i]` компонента в `manifest.json` — то есть placeholder-текст, зашитый в HTML-образец компонента внутри `unisender_components.zip`. Порядок соответствует порядку появления этих строк-образцов в HTML-файле компонента (`_replace_text_once` заменяет их последовательно, `mail_project/generation.py:172-175, 578-592`).

Примеры реальных `sample_text` из `manifest.json` (иллюстрируют, что бот НЕ подписывает поля):

| Модуль / элемент | `sample_text` (в порядке ввода) | Что это по факту |
|---|---|---|
| Кнопки / «Зелёная кнопка на всю ширину» | 1 строка: `"ЗАПИСАТЬСЯ НА ЭКСКУРСИИ"` | текст на кнопке |
| Текстовые блоки / «Заголовок 48px» | 1 строка: `"Все стили за одну встречу"` | заголовок блока |
| Авторы / «Один автор 1» | 2 строки: имя, должность | подпись автора |
| Дополнительные Баннеры / «Вариант 1» | 4 строки: дата, заголовок, текст, CTA-надпись | карточка анонса |
| Большие контентные блоки / «Вариант 1» | 9 строк: дата, заголовок, 2 тега, ещё тег, текст, имя автора, должность, CTA | составной блок |
| Контентные блоки / «Вариант 1» | 10 строк (5+5, два "столбца") | две карточки в одном компоненте |

Менеджеру в боте видно только число («10 строк, каждая с новой строки») — **без подписи, что означает каждая конкретная строка** (заголовок это, кнопка, тег или подпись автора). Соответствие «строка → назначение» существует только в `manifest.json`/HTML-образце компонента, но не показывается в диалоге.

## 4. Как строки связаны с визуальными элементами компонента

- Строки подставляются в HTML компонента функцией `build_generic_block()` (`mail_project/generation.py:578-592`): каждая `sample_text[i]` заменяется на `texts[i]` строго по порядку, один раз (`str.replace(..., count=1)`).
- Ссылки (`href="#"` в HTML-образце, `variables[].type == "link"` в manifest) **в этом flow не запрашиваются и не заполняются** для контентных компонентов. `build_generic_block()` работает только с текстом; вызов, который умеет подставлять реальные ссылки (`_replace_nth_href_hash`), в `run_selected()` (используется Telegram-flow) не вызывается ни разу — он используется только в отдельном, не связанном с ботом пути `build_card_block()`/`run()` (batch-режим из content YAML, не из Telegram).
- Проверено на фактической сборке `builds/20260904-007`: в готовом `generation/email.html` **7 ссылок остались `href="#"`** — то есть кнопки/CTA у контентных компонентов физически ведут в никуда после генерации через бота.
- **Hero (Баннеры) — отдельный и наиболее нетривиальный случай.** В диалоге для Hero (`choose_hero`, `handlers/generation.py:312-320`) вообще нет шага ввода текста — сохраняется только `{"module", "element"}`. В `run_selected()` (`mail_project/generation.py:642-660`) для Hero вызывается **только** заполнение картинок (`_fill_component_images`), замены текста нет вообще. Это подтверждено на реальной сборке: `sample_text` выбранного Hero-компонента («…текст на фоне баннера…», «Записаться на экскурсии» и т.п.) найден **дословно** в готовом `email.html` — то есть Hero всегда выходит с исходным placeholder-текстом библиотеки, а не с текстом, который ввёл бы менеджер (ввести его негде).
- Header и Footer вставляются в письмо как есть, без подстановки текста — они трактуются кодом как «системные» компоненты (см. докстринг `run_selected()`, `mail_project/generation.py:599-601`).
- Итог: реально управляемый текстом менеджера элемент — только контентные компоненты цикла (шаг 6). Hero, Header, Footer текстом менеджера не наполняются в этом flow.

## 5. Как эти данные попадают в Generation

Путь данных:

1. `handlers/generation.py` копит выбор в FSM-состоянии (`state.update_data`): `header`, `hero`, `footer`, `content_blocks` (список `{"module", "element", "texts": [...]}`), `schedule_enabled`.
2. По кнопке «Завершить и скачать» (`finish_generation`, `handlers/generation.py:453-486`) собирается словарь `selection` и передаётся в `gensvc.generate_email(build_id, selection)`.
3. `services/generation_service.py:190-204` вызывает `verify_build()` (проверка целостности build через `build_manager.py`), затем **напрямую** (в потоке, `asyncio.to_thread`) вызывает `generation.run_selected(build_dir, selection)` из `mail_project/generation.py`.
4. `run_selected()` (`mail_project/generation.py:595-729`) собирает HTML компонентов в порядке header → hero → content_blocks → schedule (если включён) → footer, пишет `build_dir/generation/email.html` и `build_dir/generation/images.json`.
5. Бот отдаёт менеджеру готовый `email.html` документом.

Никакого промежуточного хранения выбора вне FSM-состояния текущей Telegram-сессии нет: если сессия/бот перезапустится до нажатия «Завершить», собранные данные теряются (FSM в памяти — `MemoryStorage()`, `main.py:32`).

## 6. Как устроены изображения / image-slot'ы

**Факт, подтверждённый кодом и реальной сборкой: менеджер не загружает изображения нигде в этом flow.** В `handlers/generation.py` нет ни одного обработчика `F.photo`/`F.document` для изображений, нет состояния для их ожидания — весь диалог работает только с текстом и служебными файлами (`XLSX`, `SCHEDULE.txt`, `HTML` для QA).

Как это выглядит на уровне кода:

- В `selection` есть необязательный ключ `"images"` (список URL) у Hero и у каждого `content_block` — по докстрингу `run_selected()` (`mail_project/generation.py:610-621`), но **в Telegram-диалоге этот ключ никогда не заполняется** (в `handlers/generation.py` нет кода, который бы его туда добавлял).
- `_fill_component_images()` (`mail_project/generation.py:212-239`) заполняет столько image-slot'ов, сколько указано в `variables[].type == "image"` компонента в manifest.json, по позиции. Так как `real_urls` всегда пустой список, **каждый image-slot всегда получает placeholder**, а не реальное изображение.
- Placeholder генерируется функцией `_missing_image_placeholder_src()` (`mail_project/generation.py:106-130`) — это **сгенерированный на лету SVG data-URI** (жёлтый прямоугольник пунктиром, с подписью размера в px и текстом `alt`), а не файл с диска.
- Каждый заполненный slot попадает в `generation/images.json` с полями `slot_id`, `block`, `purpose`, `alt`, `source` (всегда `null` в текущем flow), `width`. Пример из реальной сборки `builds/20260904-007/generation/images.json`: 6 записей (`hero_01`…`hero_04`, `content_01`, `content_02`), у всех `"source": null`.
- В сгенерированном `email.html` этой же сборки — 6 SVG-плейсхолдеров (`data:image/svg+xml;base64,...`), т.е. 1-в-1 совпадает с `images.json`.
- Header/Footer изображения (логотипы и т.п.) в этот процесс не попадают вовсе — они «системные assets» и остаются как в каноническом компоненте (это соответствует `mail_project/IMAGE_SLOTS.md`, раздел 2.1).

**Несоответствие документации и кода** (зафиксировано как факт, без предположений о причине): `mail_project/IMAGE_SLOTS.md` (разделы 4–6) описывает другой протокол — маркер `IMAGE_MISSING_<slot_id>` в `src` и универсальный **файловый** placeholder-asset `6fea2cfd-955f-4aab-89d6-c3cb52deb89f.png` (из `MGI_UNISENDER_ASSETS.md`). Фактическая реализация (`_missing_image_placeholder_src`) использует не этот маркер и не этот файл, а собственный сгенерированный SVG data-URI. `slot_id`, `alt` и «1 slot = 1 изображение» — эти принципы IMAGE_SLOTS.md соблюдены и в коде.

Замена placeholder'а на реальное изображение после генерации — вне бота: правка `src` в готовом `email.html` руками/другим инструментом; сам бот механизма «дозагрузить изображение в существующий build» не предоставляет.

## 7. Есть ли сейчас AI-обработка текста

**В flow «Генерация письма» (и во всём `mail_project/*`, задействованном ботом) — AI-обработки текста нет.**

Проверено:
- `mail_project/generation.py` и `mail_project/qa.py` не импортируют `openai` и не делают сетевых вызовов к LLM. `qa.py` — чисто структурное сравнение HTML с каноном (токенизация тегов, `difflib`), без анализа смысла текста.
- `services/generation_service.py` только оборачивает `build_manager.py` (subprocess) и функции `generation.py`/`qa.py` — тоже без AI.
- OpenAI используется в проекте только в двух **других**, не связанных с Email-рассылками местах: `services/openai_service.py` (анализ текста договора, используется в `handlers/contract.py`, промпт `prompts/contract_check.txt`) и `services/html_service.py` (форматирование произвольного текста в HTML, тоже используется только в `handlers/contract.py`, промпт `prompts/html_format.txt`). Оба — часть отдельного раздела бота «Проверка договора», не входят в `main.py` роутер `generation`.

Тексты, которые вводит менеджер для контентных компонентов, попадают в HTML **как есть** (только HTML-экранирование через `_escape_html_text`) — без какой-либо генерации, рерайта или проверки смысла AI.

## 8. Что в текущем процессе непонятно менеджеру и почему

Всё ниже — прямое следствие фактов из пп. 1–7, а не предположение:

1. **Строки не подписаны.** Бот просит «10 строк, каждая с новой строки», но не говорит, что означает строка 1, 2, ..., 10 (заголовок? кнопка? имя автора?). Единственный источник этой информации — порядок `sample_text` в `manifest.json`, менеджеру недоступный.
2. **Hero не даёт ввести текст вообще**, хотя выглядит как обычный шаг выбора компонента наравне с Header/Footer/контентными блоками — менеджер может не понимать, что для Hero весь текст останется библиотечным placeholder'ом (это видно только по факту, что бот не задаёт вопрос про текст на этом шаге).
3. **Ссылки (кнопки/CTA) контентных компонентов никогда не запрашиваются** — менеджер вводит текст кнопки, но не URL, куда она ведёт; в письме кнопка ссылается на `#`. Внешне процесс выглядит завершённым (письмо сгенерировано, скачано), но часть ссылок нерабочая.
4. **Изображения нигде не загружаются**, при этом бот не сообщает об этом явно в диалоге — менеджер получает готовый `email.html`, где вместо изображений — плейсхолдеры, без предупреждения в самом чате о том, сколько slot'ов и что с ними нужно сделать дальше (список есть только в файле `images.json`, который бот менеджеру не отправляет — файл остаётся в `build_dir`, наружу уходит только `email.html`).
5. **Расхождение между `IMAGE_SLOTS.md` и фактическим placeholder'ом** (см. п.6) — если менеджер или другой участник процесса ориентируется на документацию, а не на код, ожидания по формату placeholder'а (файл-asset с фиксированным UUID vs сгенерированный SVG) не совпадут с тем, что реально в HTML.
6. **Нет предпросмотра компонента перед вводом текста.** Менеджер выбирает элемент по названию (`"Вариант 1"`, `"Зелёная кнопка на всю ширину"` и т.п.) вслепую — без картинки/превью того, как компонент выглядит и куда лягут строки.
