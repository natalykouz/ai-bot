# MVP_STATUS.md

Фиксация текущей точки разработки Letteros → UniSender migration перед сбросом контекста. Все изменения ниже — только локальные (не закоммичены/не запушены на момент записи).

## Текущий результат

Реализован и протестирован pipeline "старое Letteros HTML → распознанные существующие Letteros-компоненты → существующие canonical UniSender-компоненты → собранное готовое письмо". Текущая реализация — файлы:

- `letteros_recognition.py` — этап 1: распознавание. `recognize_components()` — структурное сопоставление + 4 класса content-aware/module-level fallback'ов (описаны ниже).
- `letteros_adapt.py` — этап 1.5: адаптация/пересборка оболочки и содержимого найденного блока в canonical UniSender HTML.
- `letteros_migrate.py` — этап 2: сборка письма целиком (`migrate_letter()`), включая замену расписания.
- `generation.py` — источник переиспользуемых механизмов (image-slot, `_remove_hide_row`/`_remove_hide_td`, сборка расписания, сборка итогового документа); в рамках этой задачи в него добавлены только `_remove_hide_td()`/`_scan_balanced_td_end()` — минимальное расширение существующего паттерна `_remove_hide_row()`.
- `test_letteros_recognition.py`, `test_letteros_adapt.py`, `test_letteros_migrate.py` — тесты всех трёх модулей.
- Fixtures: `letteros_components.zip` (121), `unisender_components.zip` (121), `manifest.json`, `letteros htmls/` (4 real production-письма — development/regression fixtures, см. ниже).

## Принятые архитектурные решения

Не пересматривать без новой причины:

- migration превращает распознанные Letteros-блоки в **существующие** canonical UniSender-компоненты — не в собственный произвольный HTML;
- новые canonical-компоненты для этой задачи не создаём и не будем создавать неявно;
- Letteros tracking href (`api.letteros.com/pixel/.../link/...`) удаляются целиком; исходный URL внутри (base64) не восстанавливается — это делает СММ вручную в UniSender;
- изображения переносятся через существующий механизм image-slot (`generation._fill_first_local_image`) — становятся обычными UniSender image-компонентами/слотами, а не сырым HTML;
- опциональные узлы canonical-компонента (0/1/2 повторяющихся элемента и т.п.) обрабатываются через уже существующий механизм `letteros-hide`/`_remove_hide_row`/`_remove_hide_td` — не через придуманный контент и не через отдельную новую архитектуру optional-элементов;
- старое расписание ("Мероприятия") заменяется целиком через уже существующий SCHEDULE.txt pipeline (`generation.build_schedule_blocks`) — старое содержимое не переносится;
- неподдержанный блок не заставляет MVP угадывать его структуру — миграция останавливается с явной причиной (`MigrationError`), не выдаёт частичный/подобранный "на глаз" результат;
- для MVP допускается ручной fallback для неподдержанных блоков (конкретный UX ручного fallback — предмет следующего этапа, не этого);
- библиотека canonical-компонентов проверена и признана полной: `letteros_components.zip` 121, `unisender_components.zip` 121, `manifest.json` 121 уникальных — вопрос "неполной библиотеки" закрыт как гипотеза, дальнейшие STOP не являются следствием нехватки файлов;
- 4 текущих real Letteros-письма (`letteros htmls/`) — development/regression fixtures для этой конкретной работы, **не** доказательство полного покрытия всех production-вариантов Letteros.

## Что уже проверено

**Тесты:** 90/90 зелёных (`test_letteros_recognition.py` + `test_letteros_adapt.py` + `test_letteros_migrate.py`).

**Реализованные классы production-вариантов recognition/adaptation:**
1. **wrapper_stripped** — production-блок без внешней card-обвязки/MSO ghost-table (найден по внутренней структуре, canonical-обвязка собирается заново). Покрывает картинки (`Изображения/Изображение шириной 600px`) и кнопки (`Кнопки/...`).
2. **module-level "Мероприятия"** — старое расписание распознаётся на уровне модуля (без точного `Расписание N`, т.к. число событий/дней в production переменное) по устойчивой day-шапке; конкретный элемент не важен — блок всё равно целиком заменяется новым расписанием.
3. **heading_text_injection** — заголовки `Текстовые блоки/Заголовок NNpx` распознаются по font-size (устойчивый признак), в canonical-структуру переносится только чистый извлечённый текст, ручное форматирование production (`<strong>`/`<span>`/лишние классы) не переносится.
4. **grid_content_injection** — 2-колоночный grid `Контентные блоки/Вариант 2-4` (одна structural family, отличается только accent-цветом item'а); per-item распознаётся accent (белый/teal/коралл — только 3 уже существующих в библиотеке), 0/1/2 tag-pild через `letteros-hide`/`_remove_hide_row`/`_remove_hide_td`.

**Найденные и решённые проблемы:**
- Letteros-экспорт систематически теряет `letteros-hide` (единственный признак, различающий одинаковые по тегу/атрибутам соседние опциональные узлы в structural_match) — решено content-aware recognition вместо попытки "починить" структурное сравнение.
- Ложный положительный матч (`"Контентные блоки/Место"` внутренне совпадал с `"Заголовок 28px"` без обвязки) — исправлено сужением условия входа в content-aware классы (требуется primary fingerprint collision).
- "Проходные" `<table>`-обёртки без содержания (nested duplicate scan) оставляли gap между распознанными блоками — решено расширением диапазона match'а на всю внешнюю обёртку при сохранении вложенного содержимого для пересборки.
- MSO column-switch комментарий "путешествовал" вместе с переиспользуемым item-шаблоном grid'а на чужую позицию — вынесен в отдельный connector, не зависящий от источника содержимого item'а.
- RAW_IMAGE_PASSTHROUGH (промежуточное решение, сохранявшее сырой HTML картинки) полностью удалён и заменён нормальной конвертацией в canonical `Изображения/...` компонент.

**Известные текущие ограничения (не исправлены, не в счёт этого MVP):**
- Франшиза / Казань: STOP на блоках с иным значением атрибутов card-обвязки (`padding: 15px` вместо `10px 15px`; `padding: 30px 15px 4px` + border-radius) — не относится ни к одному из 4 реализованных классов.
- Мск / ГИ special: после устранения STOP на grid — новый STOP на блоке семейства "Авторы/Один автор N" — не диагностировался и не реализовывался.
- Recognition не покрывает весь Letteros production HTML целиком ни для одного из 4 fixtures — `migrate_letter()` по-прежнему останавливается на всех четырёх, просто на более поздних/иных фрагментах, чем в начале работы.

## MVP

**Вход:** старое Letteros HTML + SCHEDULE.txt.

**Результат:**
- готовый UniSender-совместимый HTML;
- распознанные блоки — редактируемые (`em="block"`) UniSender-компоненты, а не сырой HTML;
- старое расписание заменено новым (из SCHEDULE.txt);
- Letteros tracking href удалены;
- неподдержанные блоки не ломают весь результат целиком (текущая реализация: явная остановка с причиной — `MigrationError`, а не частичный результат; конкретная форма "не ломает" для UX — предмет следующего этапа);
- пользователь получает понятное предупреждение о блоках, требующих ручной работы.

Telegram UX пока **не реализован** — весь pipeline сегодня вызывается только напрямую (`migrate_letter()`), не из бота.

## Что НЕ делаем сейчас

- не пытаемся покрыть все возможные Letteros production-варианты;
- не делаем полный audit всех 121 компонентов перед MVP;
- не создаём новые canonical-компоненты;
- не восстанавливаем старые Letteros tracking URL;
- не автоматизируем неизвестные блоки через угадывание структуры/контента;
- не продолжаем бесконечно расширять recognition ради каждого нового обнаруженного STOP.

## Следующий этап

Только:

1. проверить текущий Telegram flow (как сегодня устроен ввод/загрузка старого письма и SCHEDULE.txt в боте);
2. минимально подключить существующий migration engine (`letteros_migrate.migrate_letter()`) к Telegram;
3. реализовать MVP UX (включая понятное предупреждение о `MigrationError`/блоках, требующих ручной работы);
4. затем — acceptance test на нескольких **новых** реальных Letteros-письмах, не входивших в текущие 4 development fixtures.
