# BUILD_MANAGER.md

## Назначение

`BUILD_MANAGER.md` определяет правила создания идентифицированной production-сборки.

Build Manager фиксирует конкретный набор актуальных файлов, используемых
в последующих этапах production-процесса.

Главный принцип:

> Каждый production-запуск имеет собственный `BUILD_ID` и собственный
> зафиксированный source set. Последующие этапы работают только с этим
> source set.

## 1. BUILD_ID

Каждой сборке присваивается уникальный `BUILD_ID`.

Формат:

`YYYYMMDD-NNN`

где:

* `YYYYMMDD` — дата создания сборки;
* `NNN` — порядковый номер сборки за эту дату.

Пример:

`20260903-001`

## 2. Source set

Перед созданием сборки определяется актуальный набор файлов проекта,
необходимый для production-процесса.

В source set входят только актуальные файлы.

В частности:

* production MD-файлы с правилами;
* `manifest.json`;
* актуальная библиотека canonical HTML-компонентов;
* постоянные справочники и assets, необходимые production-процессу.

Исторические файлы, архивы, старые версии и ранее проиндексированные версии
в source set не включаются.

## 3. Фиксация source set

При создании `BUILD_ID` каждый файл source set копируется в каталог сборки.

После копирования последующие этапы не обращаются к исходному файлу проекта.

Source set конкретной сборки является неизменяемым.

Изменение исходного файла проекта не изменяет уже созданную сборку.

Для изменённого source set создаётся новый `BUILD_ID`.

## 4. SHA-256

Для каждого файла source set рассчитывается SHA-256 содержимого.

Хэш сохраняется в `build.json`.

Для каждого файла фиксируются:

* относительный путь;
* SHA-256.

## 5. Структура сборки

```text
builds/
└── <BUILD_ID>/
    ├── build.json
    ├── source/
    ├── input/
    ├── schedule/
    ├── generation/
    └── qa/
```

На этапе Build Manager создаются:

* `build.json`;
* `source/`;
* `input/`, если переданы файлы текущего выпуска.

Каталоги `schedule/`, `generation/` и `qa/` используются последующими
этапами.

## 6. build.json

`build.json` содержит:

* `build_id`;
* дату создания;
* список файлов source set;
* SHA-256 каждого файла.

Пример:

```json
{
  "build_id": "20260903-001",
  "created_at": "2026-09-03T14:30:00",
  "sources": [
    {
      "path": "rules/EVENTS_RULES.md",
      "sha256": "..."
    },
    {
      "path": "rules/GENERATION_RULES.md",
      "sha256": "..."
    },
    {
      "path": "components/manifest.json",
      "sha256": "..."
    }
  ]
}
```

## 7. Проверка целостности

Перед передачей сборки следующему этапу проверяется:

* все файлы source set существуют;
* содержимое каждого файла соответствует сохранённому SHA-256.

Если проверка не пройдена, сборка считается недействительной.

Запрещено автоматически искать замену отсутствующему или изменённому файлу.

## 8. Ограничение источников

Build Manager не использует:

* ChatGPT Project как источник файлов;
* индексированный контекст Project;
* исторические версии;
* архивные файлы;
* ранее созданные рассылки;
* старые выгрузки;
* старые версии проектных документов.

Если необходимый актуальный файл отсутствует, сборка не создаётся.

## 9. Граница ответственности

Build Manager только фиксирует source set конкретной сборки.

Он не:

* обрабатывает расписание;
* выбирает компоненты;
* генерирует HTML;
* выполняет QA;
* обрабатывает изображения.

Эти операции выполняются последующими этапами production-процесса.
